# 為什麼 gstack 的邏輯可以移植到劇本開發

## 核心同構性

gstack 的本質洞察是：**軟體開發的品質問題不是工具問題，是流程問題**。最昂貴的 bug 不是寫程式時產生的，而是架構決策錯誤後，整個 build 階段都在蓋一棟基礎有問題的房子。

好萊塢劇本開發有完全相同的問題。最昂貴的「bug」不是爛台詞，而是：
- 概念階段沒有驗證，拍到一半發現故事根本站不住腳
- 結構不鎖定就進入場景寫作，導致 Act II 崩塌要全部重寫
- 主角動機從第一頁就不清楚，到第七稿還在修

兩個領域都在解決同一個問題：**前期的決策失誤，在後期付出指數級的代價**。

## 角色對照的深層邏輯

### CEO Review ↔ Showrunner

gstack 的 CEO review 問的是：「這個產品值得建嗎？市場在哪裡？」它的目的是在投入大量開發資源之前，先用業務視角審視整個方向。

Hollywood EP 的視角完全相同，只是換了一套語言：
- 「Comp titles 是什麼，它們表現如何？」= 「有沒有 product-market fit？」
- 「是 Netflix 的作品還是 A24 的作品？」= 「這個垂直市場是哪個？」
- 「能撐六季嗎？」= 「這個 product 有長期成長潛力嗎？」

兩者都是在做同一件事：**在進入開發流程之前，先做一次不帶情感的可行性審查**。

### Design Review ↔ Story Editor

gstack 的 design review 以「抓 AI slop」著稱。它的問題是：「這個設計看起來像是 AI 生成的，還是真的有人在後面思考過？」

Story editor 做的事在結構上完全相同：
- 「這個角色是工具還是人？」= 「這個 UI 元件是樣板還是有設計意圖？」
- 「台詞有潛台詞嗎？」= 「這個按鈕文字有考慮過使用者心理狀態嗎？」
- 「主角在被動等待事情發生嗎？」= 「這個 flow 在等使用者，還是在引導使用者？」

**劇本 slop 和代碼 slop 的成因相同**：沒有人為結果負責，只是在執行生成。

### Eng Manager Review ↔ Structure Architect

gstack 的 eng review 鎖定架構：資料模型、API 介面、模組邊界。目的是在大量程式碼落下之前，確保地基是對的。一旦資料庫 schema 在生產環境使用了，改動的代價是整個 migration。

劇本的「地基」是結構。Blake Snyder 的 15 個 beats 不是美學選擇，是觀眾神經系統的生理需求：
- 第 12 頁的催化劑（inciting incident）如果不存在，觀眾的注意力在第 15 分鐘就流失了
- 第 55 頁的中點（midpoint）如果沒有反轉，整個 Act II 會感覺是在踩水
- 第 75 頁的暗夜之魂（dark night of the soul）如果缺席，最終勝利的情緒爆發就沒有對比值

**改第三稿的結構和改生產環境的資料模型代價相同**：你必須把所有建在上面的東西都推倒重建。

### QA (Playwright) ↔ Table Read

這是最完美的映射。

gstack 的 `/qa` 不是靜態分析，它開一個真實的瀏覽器，模擬真實使用者，點擊真實路徑，然後報告哪裡壞了。它的關鍵假設是：**有些 bug 只有在真實的執行環境裡才會出現**。

桌讀（table read）的邏輯完全相同。劇本在紙上看起來沒問題，但演員坐下來大聲讀的那一刻，你才會發現：
- 「這場戲在頁面上看起來有情感，但沒有人在笑或有反應」= UI flow 在設計稿裡看起來順，但真實使用者一直點錯地方
- 「這場戲之後房間裡很安靜」= 某個功能上線後使用量是零
- 「同一個故事點被說了三次，第二次就沒人在聽了」= 某個 onboarding 步驟被使用者跳過

兩者都在模擬真實接收環境，因為**靜態審查無法模擬動態體驗**。

## 關鍵差異：Hollywood 開發的獨特挑戰

gstack 可以移植的地方很多，但有幾個根本差異值得注意：

### 1. 主觀性 vs. 客觀性

程式碼有對錯：測試過了就是過了，沒過就是沒過。劇本的「對錯」更接近「在這個特定觀眾群裡，在這個特定的文化時刻，這個故事有沒有共鳴？」

這意味著 skill 的設計不能給「正確答案」，只能給**有據可查的診斷邏輯**。`/story-edit` 不說「這個台詞爛」，它說「這個台詞說出了角色正在感受的事，但角色為什麼不直接說出來？那個阻力是什麼？」

### 2. 非線性修改 vs. 版本管理

程式碼有 git，每次改動可以追蹤、回滾、比較。劇本修改傳統上是混亂的——第七稿可能是第三稿和第五稿的混合體。

這個 stack 的每一個 skill 都需要**產出版本化的 artifact**（帶日期、版本號的輸出），而不只是建議。

### 3. 多個創意聲音 vs. 單一真相來源

軟體架構最終有一個決策者（技術主管）。好萊塢開發流程涉及編劇、製片、播出方、導演、演員，每個人都有改劇本的權力。

`/showrunner` 和 `/story-edit` 的輸出需要設計成**談判的起點**，而不是指令。格式應該是「這裡有三個版本的選擇，以及每個選擇的代價」，而不是「改成這樣」。

## 最重要的借鑑：Kill Gate

gstack 最被低估的設計是：CEO review 可以 **hard stop** 整個流程。不是「有一些顧慮」，而是「這個方向不對，我們不繼續」。

好萊塢開發流程最大的浪費，是在一個已經知道站不住腳的概念上繼續投入的沉沒成本：製片公司花了六個月開發一個主角動機從第一天就不清楚的概念。

這個 stack 的 `/showrunner` 和 `/story-edit` 都設計了明確的 **kill gate**——輸出不只是建議，而是二元的 GO / NO-GO 裁定，附上具體理由。

---

## 完整工作流程狀態機

```
[原始想法]
    ↓
/pitch
    → 輸出：logline、premise、comp titles、中心戲劇問題
    ↓
/showrunner  ←── KILL GATE
    → GO：可行性報告、平台建議
    → NO-GO：停止，附理由
    ↓
/structure
    → 輸出：beat sheet、轉折點圖、頁數預算
    ↓
/story-edit  ←── KILL GATE（在初稿之前）
    → CLEAN：進入 /draft
    → ISSUES：先修概念層問題，再 /draft
    ↓
/draft
    → 輸出：場景初稿（標準格式）
    ↓
/script-doctor
    → 輸出：問題診斷 + 修改建議（依結構/場景/對白三層分類）
    ↓
/table-read
    → 輸出：逐場 kill/fix/keep 裁定 + 節奏圖
    ↓
/production-lock
    → 輸出：格式合規劇本 + 法律清理清單 + 修改頁碼記錄
```
